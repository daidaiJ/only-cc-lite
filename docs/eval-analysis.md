# only-cc-lite 真实会话压缩评估分析

> 基于真实 AI 编程助手会话日志的评估，不含任何用户隐私数据。

## 测试数据

| 维度 | 数值 |
|------|------|
| 压测会话数 | **98 个**（Claude Code 2 个 + Qwen Code 96 个） |
| 对话轮次 | 4,210 |
| 总 input tokens | 3.28 亿 |
| 涉及模型 | mimo-v2.5-pro、minimax-m2.7、kimi-k2.6、glm-5、glm-4.7-flash、deepseek-v4-flash、qwen3.6-plus 等 |

会话覆盖了日常编程助手使用的典型场景：代码编写、调试、重构、构建运行、搜索定位等。

## 总体指标

| 指标 | 数值 |
|------|------|
| User 内容（可压缩） | 10.3 MB |
| Assistant 内容（保留不动） | 3.3 MB |
| Tokens 节省 | 103,256 |
| Bytes 节省 | 452,770 |
| **整体 User 压缩率** | **4.4%** |

## 场景收益分析

### ✅ 收益明显的场景

以下场景 user 消息中包含大块结构化内容，压缩效果显著：

| 场景 | 压缩策略 | 单轮压缩率 | 典型触发条件 |
|------|---------|-----------|------------|
| **构建失败日志** | log_compressor | 50-100% | `npm run build`、`cargo build` 输出大量错误/警告 |
| **运行时错误堆栈** | log_compressor | 70-100% | Python traceback、Node.js unhandled rejection |
| **代码搜索结果** | search_compressor | 50-80% | grep/ripgrep 返回大量 `file:line:content` 匹配 |
| **Git diff 输出** | diff_compressor | 40-60% | `git diff` 输出涉及多文件变更 |
| **JSON 数据** | smart_crusher | 60-90% | API 响应、配置文件、package.json 等大 JSON |

**典型案例**：一个 28 轮的会话中，第 1 轮就压缩了 14,790 tokens（构建日志），单轮压缩率 100%。

### ❌ 几乎无收益的场景

以下场景占绝大多数轮次，但 user 消息太小或无结构化内容：

| 场景 | 占比 | 原因 |
|------|------|------|
| **短指令对话** | ~60% 轮次 | "fix this bug"、"add a test"、"refactor this" 等 < 500 bytes |
| **纯文本粘贴** | ~15% 轮次 | 错误描述、需求说明等非结构化文本 |
| **小文件内容** | ~10% 轮次 | 单个函数/配置片段，< 5KB |
| **对话式交互** | ~10% 轮次 | 追问、确认、解释等 |

**98 个会话中 73 个（74%）未产生任何压缩**，因为整个会话过程中没有出现大块结构化内容。

## 典型使用模式分析

基于 98 个会话的使用模式：

1. **主力模型**: mimo-v2.5-pro 占绝大多数会话，其次为 minimax-m2.7、kimi-k2.6、glm-5
2. **会话长度**: 从 1 轮到 338 轮不等，中位数约 30 轮
3. **工作类型**: 日常编程（代码编写、调试、重构）、项目探索（搜索、阅读代码）、构建测试
4. **User 消息特征**: 大多数是简短指令 + 工具调用结果，只有执行构建/搜索等工具后才产生大块内容

### 与会话长度的关系

| 会话轮次 | 压缩情况 |
|---------|---------|
| 短会话 (< 10 轮) | 通常无压缩，除非首轮就有大日志 |
| 中等会话 (10-50 轮) | 部分有压缩，取决于是否触发构建/搜索 |
| 长会话 (50+ 轮) | 更可能遇到构建失败，但平均压缩率不一定更高 |

**结论：压缩收益与会话长度无关，与是否触发"重内容"工具调用强相关。**

## 压缩策略命中统计

| 策略 | 命中轮次 | 贡献占比 |
|------|---------|---------|
| log_compressor | 57 turns | ~85% |
| diff_compressor | 8 turns | ~8% |
| search_compressor | 2 turns | ~5% |
| smart_crusher | 1 turn | ~2% |

**log_compressor 是绝对主力**，识别构建/运行日志中的 ERROR、WARN、Traceback 等模式。

## 结论

only-cc-lite 在真实编程助手场景下的整体 user 压缩率为 **4.4%**。这个数字反映了编程助手的实际使用特征：

- **大部分轮次是短指令**，没有可压缩的大块内容
- **收益集中在"重内容"场景**：构建失败、搜索结果、大 diff — 这些场景单轮可节省 50-100% tokens
- **增量压缩模型的合理性**：只在有价值的地方压缩，不干扰正常短对话，不破坏 assistant 消息的前缀缓存

对于重度使用构建/调试/搜索的开发者，长期累积的 tokens 节省会更可观。对于以对话为主的轻量使用，压缩收益有限但也不会引入额外开销。
